# Revision performance method

The raw directory is outside the projects. Each comparison uses identical CLI, functional workload, diagnostic level and Elasticsearch transport settings in alternating arm order. The candidate comparison sets `QAAS_USAGE_ENABLED` false or true on the same final binary. HTTP aggregation is configured identically in both arms. A separate merge-base comparison uses unmodified historical entrypoints and matched destinations. Hashes identify the runtime, Servers assembly and CLI entrypoint in every row. The closed port simulates refusal. The healthy and slow relays forward the native logging sink to real Docker Elasticsearch. Slow mode delays bulk writes one second after accepting otherwise normal startup connections.

The CLI wall time includes process startup and shutdown. OS process times measure CPU. Windows high-water working set and sampled private bytes quantify memory. A large Runner configuration executes 128 real named assertions and verifies their presence in diagnostics. A separate cross-process run has Runner request /ok from real Mocker Kestrel through an HTTP witness that asserts a 200 response with the actual healthy response bytes. It applies 128 assertions to that session, including four deliberate failures, and checks the nonzero CLI result. Exit codes and the original logs are retained. The high-RPS HTTP workload uses a warmed, persistent Node client and real Kestrel servers. Its mixed workload verifies 200, 404, 503 and 500 for every response. Reported tail latency is the 95th percentile of completed client requests, measured using a concurrency-limited load generator. Positive percentage overhead means more time or CPU for the same work; throughput differences use inverse ratios. Four HTTP pairs and at least three CLI pairs are planned per mode. Confidence intervals use paired log ratios with Student's t critical value; zero baselines use absolute changes.

Bulk accounting distinguishes entire compressed HTTP request-body bytes, uncompressed NDJSON bytes, structured usage-document payload bytes, and accepted usage and diagnostic document counts. Request-body bytes omit headers and represent payload sent on the wire. This benchmark observes raw delivery before Grafana or transforms. The relay's status check includes per-item Elasticsearch statuses. With the sink disabled or refused, accepted documents are zero. Work windows and shutdown receipts are separate. Per-server delivery totals cover the readiness request, warmup and timed traffic; periodic batches may cross the boundaries of an individual timed window. The HTTP generator is closed-loop, so quantiles describe completed requests at the specified concurrency.

Rates and dashboards are verified by separate true Runner-to-Mocker end-to-end checks. Benchmark output is local evidence. A valid delivery run does not establish a universal speed limit; summaries distinguish confidence intervals, effect size and measured callbacks.
